<objective>
Vendorizar Chromium (vía Playwright) dentro de `ExtractorApp.app`, para UNA
sola arquitectura (la nativa del Mac de build — decisión de alcance
explícita del usuario tras `17-RESEARCH.md`, que había encontrado que dos
árboles arm64+x64 sin fusionar rondan 500-700MB y requieren Rosetta 2). Con
un solo árbol, el tamaño real baja a ~250-350MB, cerca de la cifra de
referencia del ROADMAP. Extiende el patrón de bundling de la Fase 8
(codesign bottom-up, Run Script Phase) y el pipeline de firma/notarización
de la Fase 13 (`_resign_bundled_python` → `_resign_bundled_chromium`). Cierra
BUNDLEJS-01/BUNDLEJS-02 y la Fase 17.

Purpose: Que el fallback JS (SPAs sin hidratar) funcione en la app SwiftUI
sin que el usuario ejecute `pip install playwright` + `playwright install
chromium` a mano — mismo objetivo "cero dependencias externas" que ya logró
la Fase 8 con el runtime Python.

Output: `scripts/bundle-playwright.sh` (nuevo) invocado desde una Run Script
Build Phase nueva en Xcode, `scripts/verify-bundle.sh` extendido,
`scripts/release-macos.sh` con `_resign_bundled_chromium()`, `RELEASING.md`
documentando el incremento de tamaño, `PythonBridge.swift` inyectando
`PLAYWRIGHT_BROWSERS_PATH=0` en runtime — checkpoint humano en Xcode
pendiente para build real + verificación end-to-end con una SPA real (no
compilable/descargable en este sandbox: sin Xcode, sin macOS, sin acceso a
`cdn.playwright.dev` verificado, sin identidad Developer ID).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `cdn.playwright.dev` (binario Chromium de terceros) → bundle firmado localmente | Mismo modelo de confianza que python-build-standalone en la Fase 8 — binario de terceros descargado en build time, firmado por el propio pipeline del proyecto, no por el proveedor upstream |
| Chromium embebido (con `allow-jit`) → contenido web arbitrario renderizado | Chromium ejecuta JavaScript de páginas de terceros dentro de un proceso hijo de la app del usuario — superficie de ataque ya existente desde la Fase 11 (cuando el usuario instalaba Playwright a mano), ahora activa por defecto |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-17-01 | Tampering | Chromium sin firma descargado de `cdn.playwright.dev` sustituido por un binario malicioso antes de firmar | accept | Mismo modelo ya aceptado en Fase 8 para python-build-standalone — el pipeline de build corre en la máquina de confianza del autor; no hay verificación de checksum contra un hash publicado por Microsoft en este plan (mejora futura posible, no bloqueante para el alcance actual) |
| T-17-02 | Elevation of Privilege | Chromium con `allow-jit` ejecutando JavaScript arbitrario de páginas web | accept | Chromium se lanza siempre headless, sin `user_data_dir` persistente (`core.py:240`, sin cambios); hardened runtime + entitlements mínimos (solo `allow-jit` donde hace falta, nunca `disable-library-validation` ni `allow-unsigned-executable-memory` sin evidencia de que hagan falta) — ver Security Domain de `17-RESEARCH.md` |
</threat_model>
